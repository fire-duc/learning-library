전역 지침과 프로젝트 지침을 나누는 이유

서론

재고 관리 사이트와 계산기 앱을 번갈아 만든다고 생각해 보자. 두 작업 모두 결과를 한국어로 보고받고 싶지만, 실행 방법과 테스트 방법은 서로 다르다. 이 내용을 한 파일에 모두 넣으면 계산기를 수정하면서 재고 사이트의 테스트를 실행하는 혼동이 생길 수 있다. 규칙마다 적용할 범위를 나누면 이런 문제를 줄일 수 있다.

본론

어디에 적용할 규칙인지 먼저 구분한다

지침의 적용 범위: 그 규칙이 어느 작업에 영향을 미치는지를 뜻한다.

  • 모든 프로젝트에 필요한 규칙과 특정 프로그램에만 필요한 규칙은 범위가 다르다.

전역 지침: 여러 프로젝트에서 공통으로 사용할 기본 원칙이다.

  • 예를 들어 보고 언어와 중요한 결정을 질문하는 기준을 여기에 둘 수 있다.

프로젝트 지침: 해당 프로젝트에서만 필요한 규칙이다.

  • 실행 방법, 검증 방법, 문서 위치 등이 해당한다.

규칙 충돌: 같은 상황에서 두 규칙을 동시에 지킬 수 없는 상태다.

  • 단순히 설명이 서로 다른 것과는 구분해야 한다.
  • “테스트를 실행한다”와 “이 앱의 테스트 명령은 A다”는 보완 관계지만, “항상 공개 배포한다”와 “승인 전 공개 배포하지 않는다”는 충돌할 수 있다.

공통 원칙과 프로젝트의 실행 방법을 연결한다

전역에 “변경에 맞는 검증을 실행한다”를 두고, 재고 사이트의 프로젝트 지침에 구체적인 검증 명령을 적으면 역할이 이어진다. 공통 원칙을 모든 프로젝트에 복사할 필요가 없고, 사이트의 실행 방법이 바뀌면 해당 파일만 고치면 된다.

Codex의 AGENTS.md는 실행 시작 시 전역 지침과 작업 경로의 프로젝트 지침을 찾아 결합하는 방식이다. 따라서 매 명령마다 사람이 모든 파일을 새로 읽어야 한다는 뜻은 아니다. 작업 경로에 더 가까운 지침은 앞선 지침을 구체화하거나 덮어쓸 수 있지만, 시스템의 권한 제한까지 없애지는 못한다. 파일을 편집한 뒤 기존 실행에 반영됐는지는 별도로 확인해야 한다.

재고 사이트와 계산기 앱에는 다른 검증이 필요하다

가상의 재고 사이트는 데이터베이스를 사용하고, 계산기 앱은 숫자 계산만 수행한다. 전역에는 “관련 없는 사용자 데이터를 바꾸지 않는다”를 적는다. 재고 사이트에는 “검증에는 테스트용 데이터베이스를 사용한다”, 계산기 앱에는 “소수점과 음수 계산을 검증한다”를 적는다.

이렇게 나누면 목적은 공통으로 유지하면서 실행 방법은 달라진다. 반대로 테스트용 데이터베이스 규칙을 전역에 넣으면 데이터베이스가 없는 계산기 작업에도 불필요한 판단이 끼어든다. 전역 파일에 넣기 전에는 다른 종류의 프로젝트에서도 필요한 문장인지 생각하면 된다.

같은 규칙을 여러 곳에 복사하면 어긋날 수 있다

여러 파일에 같은 규칙을 복사하면 한쪽만 수정했을 때 충돌이 생긴다. 공통 규칙은 한곳에 두고, 프로젝트 파일은 고유한 정보와 필요한 예외를 설명하는 편이 관리하기 쉽다. 예외는 “이 프로젝트에서 다르게 처리할 행동”과 적용 조건이 분명해야 한다.

사람용 사용 안내와 에이전트용 작업 규칙도 구분할 수 있다. README에는 설치와 실행 절차를, AGENTS.md에는 작업 시 지킬 기준과 관련 문서 위치를 둔다. 이러한 문서 역할 배치는 관리 방법의 예시이며 모든 프로젝트가 같은 파일 구성을 가져야 하는 것은 아니다.

결론

전역과 프로젝트 지침을 나누는 핵심은 규칙의 수를 늘리는 데 있지 않다. 공통 원칙을 한 번 정의하고, 각 프로젝트에서 필요한 실행 방법을 정확히 연결하는 데 있다. 문장을 추가할 때 적용 범위와 기존 규칙과의 충돌을 함께 확인하면 유지하기 쉬운 지침이 된다.
