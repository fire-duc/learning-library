구현 완료·테스트 통과·실행 확인의 구분

서론

개발자가 ‘완료했습니다’라고 했지만 실제 사용 환경에서는 아직 실행해 보지 않았다고 하자. 완료라는 표현이 어떤 증거를 가리키는지 나누면 기대 차이를 줄일 수 있다.

본론

작성·시험·실제 실행은 서로 다른 확인 단계다

구현 완료: 요구한 동작을 수행하도록 코드를 작성한 상태다.

  • 코드가 있다는 사실과 실제 환경에서 잘 동작한다는 사실은 다르다.

테스트 통과: 정한 입력과 조건에서 기대 결과가 확인된 상태다.

  • 시험하지 않은 조건까지 검증했다는 뜻은 아니다.

실행 확인: 실제 사용할 환경에서 필요한 기능을 실행해 본 것이다.

  • 계정 권한·네트워크·파일 경로처럼 환경에 의존하는 조건을 포함한다.

가짜 응답 시험을 통과해도 실제 계정은 실패할 수 있다

세 상태를 나누면 확인하지 않은 환경까지 정상이라고 말하는 일을 줄일 수 있다. 검증에는 버전과 환경, 확인한 경로를 함께 기록한다.

가짜 서버 응답으로 주문 처리 시험을 통과해도 실제 계정의 권한이 부족하면 실행은 실패할 수 있다. 반대로 화면이 한 번 열렸다는 사실만으로 재시작과 오류 복구까지 확인한 것은 아니다. 보고할 때 ‘무엇을 구현했는가’와 ‘어떤 조건에서 무엇을 확인했는가’를 함께 적으면 다음 점검 범위가 보인다.

모의 주문 로직 테스트를 통과해도 Windows 로그인 뒤 자동 실행되는지는 별도 확인이 필요하다. 화면이 열렸다고 주문 대사(Reconciliation)까지 검증된 것도 아니다.

확인한 범위와 미검증 범위를 함께 밝힌다

검증 범위 밖을 실패로 단정할 필요는 없지만 미검증임은 밝혀야 한다. 보고는 코드 작성, 검사 결과, 실제 실행 범위를 각각 적는다.

한눈에 비교하기

아래 표는 본문의 구분을 간단히 정리한 것이다. 수치가 있는 경우 이해를 위한 예시다.

표현 뜻 추가로 필요한 것
구현 완료 코드 변경을 마침 동작 검증
테스트 통과 검사한 조건에서 통과 실제 실행 환경 확인
실행 확인 해당 환경에서 동작 관찰 다른 조건까지 보장하지 않음

결론

완료를 단계별 증거로 표현하면 남은 불확실성을 숨기지 않으면서 진행 상황을 정확히 전달할 수 있다. 미실행 검증은 실패와도 구분하자.
