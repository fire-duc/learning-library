다중 사용자 인증·권한·장부 격리

서론

사용자 A가 로그인한 뒤 주소의 주문 번호를 B의 주문 번호로 바꿨을 때 B의 기록이 보인다면, 로그인은 있지만 권한 검사가 빠진 것이다.

본론

1. 개념의 정의

개인용 도구와 다중 사용자 서비스

개인용 도구는 한 사람의 설정·데이터·실행 환경을 중심으로 설계한다. 다중 사용자 서비스는 여러 사람이 각자의 권한과 데이터를 사용하는 구조이므로 저장·처리·조회 전체에 사용자 구분이 필요하다.

인증

요청한 사람이 누구인지 확인하는 과정이다. 로그인과 세션 확인이 여기에 해당한다.

인가 또는 권한 검사

그 사람이 특정 자료를 보거나 행동을 수행할 수 있는지 확인하는 것이다. 인증된 사용자도 모든 자료를 볼 권한은 없다.

장부 격리

사용자별 기록이 조회·갱신·집계에서 섞이지 않도록 분리하는 것이다. 데이터베이스를 하나 쓰더라도 모든 접근에 올바른 사용자 범위가 필요하다.

2. 개념을 연결해 이해하기

서버에서 모든 조회·수정 요청에 소유권을 확인하고 워커·캐시·알림에도 사용자 범위를 유지한다. 사용자 ID를 요청 본문에서 그대로 신뢰하면 안 된다.

서버는 요청 본문에 적힌 사용자 이름을 그대로 믿기보다 검증된 로그인 정보에서 소유자를 판단해야 한다. 주문 조회뿐 아니라 통계 캐시·파일 다운로드·백업·알림에도 같은 범위를 적용한다. 화면에서 B의 버튼을 숨겨도 API가 B의 자료를 반환한다면 실제 경계는 없는 셈이다.

사용자별 작업 상태·비밀값과 자원 한도도 분리해야 한다. 한 사용자의 과도한 요청이 다른 사용자의 작업을 막지 않는지 확인하는 것까지 개인용 도구를 서비스로 바꾸는 범위에 포함된다.

3. 사례로 살펴보기

로그인한 A가 B의 주문 ID를 넣어 조회하더라도 B의 정보를 반환하지 않아야 한다. 집계 캐시와 다운로드 파일에서도 같은 검사를 적용한다.

4. 주의점과 확인 방법

UI 숨김은 접근 통제가 아니다. 관리자 권한, 세션 만료, 사용자별 비밀값과 백업 격리까지 실제 경로에서 검증해야 한다.

서비스 공개를 계획한다면 운영·지원·개인정보 처리 범위도 별도로 검토한다. 구체적인 적용 의무는 서비스 범위와 지역을 확인한 뒤 판단해야 한다.

결론

인증은 신원을, 권한 검사는 허용 범위를 판단한다. 사용자 구분이 모든 데이터 경로에 이어지는지 확인해야 다중 사용자 서비스의 기본 경계를 지킬 수 있다.

범위와 참고 자료
